# Assignment alignment and deliberate deviations

The assignment describes a broad production-style GCP design. This
implementation provides a working, evidence-backed demonstration within the
assessment window. The differences below are deliberate, not accidental.

| Area | Assignment | Implementation choice | Reason and tradeoff |
|---|---|---|---|
| Delivery window | One week | Prove the required application path first, then add bounded production-style controls while preserving evidence for each immutable release | This keeps a working endpoint reviewable throughout the assessment. Optional or cost-bearing controls remain explicit extensions unless enabled and live-proven. |
| Project governance | Folder-to-project hierarchy and Dev, Ops, SRE, and CI/CD roles | One personal project with explicit role boundaries | Dev has repository/lower-environment access only and no production principal; CI/CD uses a shared build identity plus separate namespace deployers; SRE uses the restricted observability reader; Ops remains the owner/operator. With no Organization or Cloud Identity groups, this demonstrates duties but not enterprise group inheritance or full separation of control. |
| Team isolation | Independent application ownership | Separate `currency-app-a` and `currency-app-b` namespaces with platform-owned guardrails and per-app deployer identities | Each pipeline can change only its workloads; RBAC, Services, runtime identities, quotas, and NetworkPolicies remain platform-owned. This supports trusted internal teams on shared clusters, not hostile-tenant isolation. |
| Project creation | Terraform should reproduce the entire setup | The dedicated project and billing link are prerequisite operator actions; Terraform imports the project and owns its persistent configuration | Project creation and billing attachment need account-level authority and should not be destroyed with the workload. A fresh deployment therefore needs an existing billing-enabled project before running the checked-in stacks. |
| Application example | The clarification leaves the business function and technology stack open | A no-input synthetic currency-rate board: public Java App A calls internal .NET App B | GET is natural for public reference data and makes the demo accessible without a form, login, customer data, or request body. Ten fixed snapshots give the refresh button visible variation while keeping verification deterministic and avoiding a live market dependency. The tradeoff is that this proves the operational architecture rather than a complex financial workflow. |
| Resource names | The application is a currency-rate demo | Application namespaces use currency names; existing `risk-*` GCP foundation identifiers stay frozen | Clusters, registry paths, dataset, and load-balancer resources were already healthy. Replacing them for cosmetic naming would add cost and risk; namespaces could be migrated without replacing the GCP foundation. |
| Global routing | Global HTTPS load balancing using MCI or MCS, followed by a GKE Ingress path | Terraform-managed global external Application Load Balancer over standalone zonal Pod NEGs; no GKE Ingress controller | App A Services register the NEGs, and the Terraform backend addresses the Pod endpoints directly. This keeps the edge graph reviewable and preserves NetworkPolicy, but it deliberately substitutes for the literal MCI/MCS and Ingress-controller products. |
| HTTPS and DNS | HTTPS endpoint behind Cloud DNS | Use the dedicated root domain `satish.store` with Cloud DNS, a Google-managed certificate, and no configured HTTP frontend | Google provides no sample hostname for this load balancer. Moving this assessment-only domain to Cloud DNS lets Google validate and renew the certificate automatically while the existing reserved IP stays fixed. The registrar nameserver change is manual. There is no port-80 forwarding rule, proxy, or redirect, so plain HTTP receives no response. This is less convenient than redirecting but matches the requirement to disallow public HTTP. |
| Cluster mode and regions | Standard or Autopilot; `us-east1` is shown as an example | Regional Autopilot clusters in `us-central1` (`b/c/f`) and `us-east4` (`a/b/c`); no node pools | Autopilot is allowed and reduces setup and operations. Repeated central `a` capacity failures led to a guarded same-name cluster replacement with `f`; east and the shared foundation stayed intact. Hard zone declarations make NEG ownership deterministic but reduce scheduler flexibility. |
| Regional replicas | Multiple scalable Pods with HPA | Three zonal App A shards and two App B replicas per region | One App A shard per declared zone gives every standalone NEG a real backend; each shard scales from one to two, preserving a total App A range of three to six. The project-wide CPU quota preference is 96, but quota is only a ceiling: it carries no direct fee, reserves no capacity, and still depends on Google approval and zonal availability. |
| Network egress and naming | Shared VPC, Private Service Access, Cloud NAT, and Cloud DNS are listed | Dedicated custom VPC with Private Google Access; Cloud DNS for the public hostname; Kubernetes DNS for cell-local App B; no Shared VPC, Private Service Access, NAT, proxy-only subnet, or default-deny egress policy | App A must reach the GKE metadata server and App B's verifier periodically retrieves Google's public signing keys. Standard NetworkPolicy cannot safely express those changing Google hostnames, so a broad IP allowlist would be brittle. Inbound NetworkPolicy remains default-deny. A production design would add FQDN-aware egress control or a service mesh/proxy. |
| State, backup, and rebuild | App B may use managed state; the HA section lists data replication, GKE etcd, and Artifact Registry backup policies | Stateless, deterministic .NET provider with no database, PV, or application state in etcd | There is no application recovery-point target to back up. Clusters and workloads are rebuilt from Terraform, Kustomize, source, and immutable full-SHA images; the assessment does not configure GKE etcd backup or a separate Artifact Registry backup/replication policy. A stateful production service would require explicit cross-region data replication, tested restore, registry retention/replication, and remote Terraform state. |
| Service mesh and security extras | Service mesh/mTLS, Secret Manager, Binary Authorization, and backups are suggested | NetworkPolicy, Google-signed App A service tokens, hardened Pods, optional Binary Authorization allowlisting, least-privilege IAM, and no public App B; mesh, dummy secrets, and backups are deferred | The signed ID token adds caller identity without a stored key. The stateless apps have no secret or volume to back up. Internal traffic remains HTTP, so this does not provide mTLS encryption. Binary Authorization is implemented but disabled live to avoid an unnecessary feature charge. |
| Binary Authorization depth | A production supply-chain design can require signed attestations | Provide an opt-in default-deny policy for Google's system images and exact `app-a`, `app-b`, and `grafana-evidence` Artifact Registry paths; keep enforcement disabled live | The implementation is ready for a separately approved test, but disabled enforcement is not a live supply-chain claim. Even when enabled, repository allowlisting trusts anyone who can push to those paths and is weaker than cryptographic build provenance. The gate requires an in-place cluster update and a non-persisting denial test. |
| Workload Identity mapping | Map Kubernetes workloads to Google service accounts | Map App A to `currency-app-a-caller`, App B to `currency-app-b-telemetry`, and the evidence-only Grafana KSA to `grafana-reader` | App A needs an audience-bound token plus trace/profiler export, App B needs trace export, and Grafana needs read-only data. Every binding names one namespace/KSA, uses short-lived credentials, and creates no key; a matching deployment gate proves the runtime mapping. |
| Delivery ownership | CI/CD for both applications | Separate App A and App B build definitions and direct deploy lanes; retain one parallel orchestrator | Either app can release independently. Simultaneous compatible changes use the coordinated command, which runs both lanes concurrently and then one aggregate gate; arbitrary direct-lane concurrency is intentionally unsupported because gates/rollback could race. The shared builder and registry remain platform boundaries; breaking APIs still need expand-contract. |
| BigQuery log scope | Export application logs and GKE control-plane/node logs | Keep application stdout in `risk_logs`; route a bounded platform sample to separate `currency_platform_logs` | Separate schemas keep application queries stable. The platform sink includes sampled control-plane/node/firewall logs plus LB, VPC-flow, and health logs with 30-day retention; matching evidence is required before claiming it live. |
| Platform log coverage | Centralize container, ingress, load-balancer, VPC, and firewall logs | Enable exact GKE control-plane/workload components, 5% VPC Flow Logs without metadata, 10% firewall/control-plane samples, and 5% LB requests (100% only for an enabled Armor exercise) | This bounds cost and sensitive network metadata. GKE logging components are live; the remaining controls require their runtime gate. |
| Observability | Logging, Monitoring, Trace, Profiler, Error Reporting, BigQuery, and Grafana | Retain the proven logs/BigQuery/Grafana/Error Reporting path; add direct keyless sampled traces for both apps and Profiler for Java App A | Trace and Profiler require matching deployed images and runtime evidence; source tests alone are not a live claim. Profiler has no equivalent supported .NET agent here, so only App A is profiled. |
| Monitoring coverage | Show Pod CPU/memory, node health, HPA events, and ingress/load-balancer traffic signals | Keep the four application panels and add explicit gates for node Ready, HPA decisions/latency, and LB request/5xx/latency metrics | Required application panels are proven. The expanded platform gates require a matching runtime evidence run. |
| Grafana hosting | Use cloud-hosted Grafana | Use a one-hour Grafana Job inside private GKE, reached only through an operator loopback port-forward | It uses a dedicated namespace, restrictive quota, read-only KSA/GSA, no Service/Ingress/Secret/PVC, and forced cleanup. This is safer than a public demo URL but not a durable shared service with SSO. The baseline evidence used a local loopback runtime, so the GKE path requires separate proof. |
| Cloud Armor | WAF inspection is part of the example flow | Provide an opt-in Standard policy with per-IP rate limiting, preview-only SQLi/XSS rules, and default allow; keep it disabled live | The checked-in Terraform keeps the control reproducible without adding a feature charge to a short-lived demo. Disabled means there is no live WAF or rate-limit claim. Enabling it requires cost acceptance, preview-log review, and a bounded denial test. |
| Regional behavior | Primary/secondary, active/active, and active/passive are all presented as options | Both cells are eligible while healthy; an unhealthy cell drains through health checks | This gives measurable recovery but not zero downtime during health convergence. Capped retries for idempotent GETs with backoff/jitter, faster health tuning, and reserved survivor capacity could reduce transition errors; that production SLO work is out of scope. |

The core requirements remain unchanged: a new GCP project, two regional GKE
clusters, Java App A as the public service, .NET App B as an internal service,
multiple Pods and autoscaling, global health-based traffic, Terraform,
structured logs, BigQuery queries, four Grafana panels, and a real
troubleshooting record.
